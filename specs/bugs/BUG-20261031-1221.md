# BUG-20261031-1221: Phone discovery fails after Bluetooth adapter renumbering

## Summary

The phone cannot discover the desktop because syauth retains an absent `hci0`
while BlueZ exposes the working controller as `hci1`.

## Reproduction

- Method: live host and radio regression in sibling syauth.
- Commands: `bluetoothctl list`, `bluetoothctl show`,
  `journalctl --user -u syauth-presenced.service -n 25 --no-pager`.
- Evidence: powered controller `50:BB:B5:B9:93:AB`, zero active advertisements;
  repeated `rotation failed ... advertise: the target object was either not
  present or removed`. BlueZ audio logs use `hci0` on October 27 and `hci1` on
  October 29–30.
- An approved daemon restart at 12:21:07 produced `orchestrator not started;
  daemon will serve socket only ... adapter set_powered: the target object was
  either not present or removed`. The status RPC still reported `state: up`.

## Expected

The daemon selects an adapter present in BlueZ and advertises the existing
bond's rotating UUID so the phone reconnects without pairing again.

## Actual

The process and RPC socket remain available with no usable Bluetooth transport.
Enabling Bluetooth on the phone cannot recreate the desktop advertisement.

## Root Cause

Sibling syauth's `crates/syauth-presenced/src/runtime.rs` initializes
`PersistentPeripheral::new(DEFAULT_ADAPTER_NAME)` with the constant `hci0`.
The named bluer adapter handle does not check object existence until a property
operation. Controller renumbering invalidates the retained handle, and even a
restart repeats the absent adapter selection.

## Fix

Select BlueZ's available default adapter for daemon startup. Preserve explicit
adapter selection for callers that request a particular controller. Runtime
recovery after another controller removal remains a separate acceptance concern.
