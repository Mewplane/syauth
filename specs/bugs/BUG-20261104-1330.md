# BUG-20261104-1330: Daemon loses the adapter at boot and permanently serves the Challenge stub

## Summary

`syauth-presenced` starts about a second after `bluetoothd`, before the
kernel has finished setting up `hci0`, so `Session::default_adapter()`
fails with "the target object was either not present or removed". The
daemon logs one `WARN`, drops the orchestrator for the rest of its
lifetime, and keeps answering `Request::Challenge` from the S-002 stub
(`reason="not-implemented"`). The PAM module maps that unknown reason to
`PAM_AUTH_ERR` and logs `unlock denied reason=unknown-reason`, so every
unlock fails until the unit is restarted by hand.

Pairing is unaffected because `syauth pair` is a separate process that
opens the adapter itself; a bond can be minted while unlocks are dead.

## Reproduction

Manual, captured on the reporter's host (boot `c73ac0295d4f45…`):

```
13:42:35.409 bluetoothd: Bluetooth management interface 1.23 initialized
13:42:36.196 syauth-presenced: WARN orchestrator not started; daemon will serve socket only
             reason="BlueZ adapter open failed: peripheral backend error:
             default adapter selection: the target object was either not present or removed"
13:42:36.323 kernel: Bluetooth: hci0: Device setup in 2624999 usecs
```

The daemon queried D-Bus 127 ms before the adapter object existed.

Wire-level confirmation, before the restart:

```console
$ printf '<CBOR a3 kind=challenge peer_id=5bbd… nonce=16B>' | socat - UNIX-CONNECT:$XDG_RUNTIME_DIR/syauth/auth.sock
a4 64 6b 69 6e 64 69 63 68 61 6c 6c 65 6e 67 65 62 6f 6b f4 …
   {"kind": "challenge", "ok": false, "signature": null, "reason": "not-implemented"}
```

After `systemctl --user restart syauth-presenced` the same probe returns
`response-timeout` (a real challenge was issued to the phone), and the
daemon log shows the full orchestrator path:

```
13:56:25 registering GATT app with pair service peers=0
13:56:25 GATT app registration accepted by BlueZ
13:56:26 phone subscribed via standard notifications
13:56:28 notify_challenge: writing frame peer_id=5bbd89ad…
13:56:33 tx peer=5bbd89ad… outcome=ok
```

The same race is visible on the preceding boot (`12:42:36`, same
message), while a mid-session restart (`12:35:12`) opened the adapter
successfully — the failure is tied to starting before the adapter is
exported, not to the store or the bonds file.

## Expected Behavior

The daemon acquires the adapter once BlueZ exposes it (or retries with
backoff), and an unlock attempt while the radio is unavailable is
reported as `adapter-missing` / `offline` so PAM falls through to the
next auth module instead of returning `AUTH_ERR`.

## Actual Behavior

`PersistentPeripheral::new_default()` fails, the orchestrator is never
constructed, and every `Request::Challenge` gets the stub answer
`reason="not-implemented"`. `outcome_reason_to_pam` does not know that
token, so it fails closed with `unknown-reason` → `PAM_AUTH_ERR`
(`crates/syauth-pam/src/auth.rs:212`). Because the process stays alive,
`Restart=on-failure` never fires; only a manual restart recovers it.

## Root Cause Analysis

1. Startup ordering. The user unit (`crates/syauth-presenced/dist/syauth-presenced.service`)
   has `WantedBy=default.target` and no ordering or readiness gate
   against `bluetooth.target` / `bluetooth.service`. With autologin the
   user manager races `bluetoothd`; the kernel's `hci0` setup finished
   127 ms after the daemon's only probe.
2. No retry. `crates/syauth-presenced/src/runtime.rs:332-337` returns
   `(None, None, None)` on any adapter-open error and the `WARN` is the
   only signal. There is no watchdog on adapter appearance/reappearance.
3. Wrong degraded reason. `crates/syauth-presenced/src/server.rs:353-357`
   answers with `STUB_CHALLENGE_REASON` when `orchestrator == None`,
   which is indistinguishable from the not-yet-implemented S-002 stub.
   The PAM taxonomy has an `adapter-missing` token but the daemon never
   emits it on this path.
4. Diagnostic blind spot. `syauth doctor` reports `doctor=ok` while the
   orchestrator is dead, and `syauth status` prints `advertising=false`
   from a constant, so neither surface shows the degraded state.

## Fix

Workaround applied on the host (survives reboots, no rebuild needed):

`~/.config/systemd/user/syauth-presenced.service.d/wait-for-adapter.conf`

```ini
[Service]
ExecStartPre=/bin/sh -c 'i=0; while [ $i -lt 120 ]; do bluetoothctl show 2>/dev/null | grep -q "^Controller " && exit 0; i=$((i+1)); sleep 0.5; done; exit 0'
TimeoutStartSec=90
```

Verified with `systemctl --user daemon-reload && systemctl --user restart
syauth-presenced`: startup log shows `GATT app registration accepted by
BlueZ` and the rotation timer.

Source-level fix (not yet applied):

- `runtime.rs`: retry `PersistentPeripheral::new_default()` with bounded
  exponential backoff and re-arm on adapter loss, instead of returning
  once.
- `server.rs` / `runtime.rs`: when the orchestrator is absent, answer
  `adapter-missing` (or `offline`) rather than the S-002 stub token.
- `syauth doctor` / `syauth status`: probe the orchestrator + GATT
  registration instead of a constant.
